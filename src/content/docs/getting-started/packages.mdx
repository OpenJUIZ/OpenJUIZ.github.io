Once you have installed the `juiz` command in [Installation](/getting-started/install/), prepare the package for the language you write components in. You only need the section for your language.

## Rust

Write components with the [juiz_sdk](https://crates.io/crates/juiz_sdk) crate, built as a shared library.
Using the same juiz_sdk version as `juiz` is the safest choice. Since juiz_sdk 0.0.30, plugins are loaded through a C function boundary (the plugin C ABI), so they load even when the juiz_sdk or rustc version differs from `juiz`. A plugin built with juiz_sdk 0.0.29 or earlier stops with an error when its version does not match.

```toml
[lib]
crate-type = ["cdylib"]

[dependencies]
juiz_sdk = "0.3.3"
```

[Tutorial chapter 1 (Rust)](/tutorial/first-process/rust/) explains `Cargo.toml` while reading the skeleton made with `juiz pkg create`.

## Python

Write components with the decorators in [pyjuiz](https://pypi.org/project/pyjuiz/) (`from juiz import juiz_process` and so on).

<Tabs syncKey="install">
<TabItem label="Install with pip">

pyjuiz comes with `juiz-cli`. There is nothing else to install.

</TabItem>
<TabItem label="Install with cargo">

As described in "Using Python Processes too" in [Installation](/getting-started/install/), install only pyjuiz, at the same version as `juiz`.

```sh
pip install pyjuiz==0.3.3
```

</TabItem>
</Tabs>

## C++ and Haskell: libjuiz_sdk

C++ and Haskell components link to libjuiz_sdk, the shared library of C functions that pass values to and from juiz.
Archives of libjuiz_sdk with the headers for each OS and CPU are on [GitHub Releases](https://github.com/OpenJUIZ/juiz/releases) (from 0.0.26).
Use the **same version** as `juiz`. juiz refuses to load a plugin built with a different version of libjuiz_sdk.

The easiest way is `install-juiz-sdk.sh` (`install-juiz-sdk.ps1` on Windows), which detects your OS and CPU. It extracts the archive to `~/.juiz/sdk/<version>` (`%USERPROFILE%\.juiz\sdk\<version>` on Windows).

<Tabs syncKey="platform">
<TabItem label="Linux">

```sh
juiz --version      # e.g. juiz 0.3.3
curl -fsSL https://raw.githubusercontent.com/OpenJUIZ/juiz/main/scripts/install-juiz-sdk.sh | sh -s -- 0.3.3
```

</TabItem>
<TabItem label="macOS">

```sh
juiz --version      # e.g. juiz 0.3.3
curl -fsSL https://raw.githubusercontent.com/OpenJUIZ/juiz/main/scripts/install-juiz-sdk.sh | sh -s -- 0.3.3
```

</TabItem>
<TabItem label="Windows">

Run this in PowerShell. Windows archives are available from 0.0.27.

```powershell
juiz --version      # e.g. juiz 0.3.3
& ([scriptblock]::Create((irm https://raw.githubusercontent.com/OpenJUIZ/juiz/main/scripts/install-juiz-sdk.ps1))) 0.3.3
```

</TabItem>
</Tabs>

The extracted directory contains:

| Path | Contents |
| --- | --- |
| `lib/` | libjuiz_sdk (`.so` on Linux, `.dylib` on macOS) and `pkgconfig/juiz_sdk.pc` for pkg-config. On Windows, the import library `juiz_sdk.dll.lib` used for linking |
| `bin/` | Windows only. The libjuiz_sdk DLL, `juiz_sdk.dll` |
| `lib/cmake/juiz_sdk/` | Settings for CMake's `find_package(juiz_sdk)` (from 0.0.27) |
| `cjuiz/include/` | C headers |
| `cppjuiz/include/` | C++ headers (`juiz/juiz.h`) |

For 0.0.25 and earlier, get the juiz source at the tag of the same version as `juiz` and build libjuiz_sdk with `cargo build --release -p juiz_sdk`.

## C++

From 0.0.27, CMake can use libjuiz_sdk through `find_package`. Point `CMAKE_PREFIX_PATH` (or the `PATHS` of `find_package`) at the extracted directory.

```cmake
find_package(juiz_sdk 0.3.3 EXACT CONFIG REQUIRED)
add_library(my_process SHARED my_process.cpp)
target_link_libraries(my_process PRIVATE juiz_sdk::juiz_sdk)
juiz_sdk_copy_runtime(my_process)   # on Windows, copies juiz_sdk.dll next to the plugin
```

`juiz_sdk::juiz_sdk` also carries the header directories and the C++17 requirement. On Windows, juiz looks for the `juiz_sdk.dll` a plugin uses in the plugin's directory (and in `PATH`), so `juiz_sdk_copy_runtime` copies it there.
[Tutorial chapter 1 (C++)](/tutorial/first-process/cpp/) explains the CMake file while reading the skeleton made with `juiz pkg create`.

Without CMake, add `cjuiz/include` and `cppjuiz/include` to the include path, and link to libjuiz_sdk in `lib` (`lib/juiz_sdk.dll.lib` on Windows).
You can also let CMake fetch libjuiz_sdk, as [cmake/Juiz.cmake](https://github.com/OpenJUIZ/juiz_examples_cpp/blob/main/cmake/Juiz.cmake) in the [juiz_examples_cpp](https://github.com/OpenJUIZ/juiz_examples_cpp) examples does.

## Haskell

Write components with [hsjuiz](https://github.com/OpenJUIZ/juiz/tree/main/bindings/hsjuiz). You need GHC 9.6 or later and cabal (Linux, macOS, Windows; Windows is supported from 0.0.27).
hsjuiz is on [Hackage](https://hackage.haskell.org/package/hsjuiz) from 0.2.6. In the `.cabal` of your package, add hsjuiz of the same version as `juiz` to `build-depends` (such as `hsjuiz ==0.3.3.*`), and write where libjuiz_sdk is in `cabal.project`. Run `cabal update` first to get the Hackage index.

```sh
cabal update
```

The commands for Windows are in the "Windows" tab below.

<TabItem label="Windows">

From 0.0.27 you can write components in Haskell on Windows (x86_64) too. You need GHC 9.6 or later (juiz's CI checks it with GHC 9.6.7).

The import library of libjuiz_sdk that Rust builds is named `juiz_sdk.dll.lib`, which GHC's `-ljuiz_sdk` cannot find.
Copy it into a separate directory under the name `juiz_sdk.lib`.

```powershell
mkdir $env:USERPROFILE\.juiz\sdk\0.3.3\import -Force
Copy-Item $env:USERPROFILE\.juiz\sdk\0.3.3\lib\juiz_sdk.dll.lib $env:USERPROFILE\.juiz\sdk\0.3.3\import\juiz_sdk.lib
```

```txt title="cabal.project"
packages: .

package hsjuiz
  extra-lib-dirs: C:/Users/me/.juiz/sdk/0.3.3/import, C:/Users/me/.juiz/sdk/0.3.3/bin
```

`import` is where `juiz_sdk.lib` for linking is, and `bin` is where GHC loads `juiz_sdk.dll` from when it runs Template Haskell.
Windows has no rpath. juiz looks for the `juiz_sdk.dll` a plugin uses in the plugin's directory (and in `PATH`), so copy `bin\juiz_sdk.dll` next to the DLL you built.

GHC on Windows has no Haskell shared libraries, so the RTS and the packages you depend on are linked statically into the DLL.
In your package's `.cabal`, write `options: standalone` in each `foreign-library`, and pass a `.def` file listing the exported functions with `mod-def-file` (cabal does not accept them in a `common` stanza).

```text title="your-package.cabal (excerpt)"
foreign-library increment_process_hs
    type:             native-shared
    if os(windows)
        options:      standalone
        mod-def-file: increment_process_hs.def
        ghc-options:  -fno-PIC
    ...
```

```text title="increment_process_hs.def"
EXPORTS
    juiz_hs_init
    manifest_entry_point
    process_factory_entry_point
```

The library you get is `<name>.dll`, without `lib`. Unlike Linux and macOS, each DLL has its own RTS, so put a Container and its ContainerProcesses into one Component (one DLL) with `juizComponent`.
On Windows, also add `-fno-PIC`. Without it, running a `case` that branches on a value of a type with 7 or more constructors (including `show` from `deriving Show`) crashes the process (GHC bug [ghc#24016](https://gitlab.haskell.org/ghc/ghc/-/issues/24016), [issue #262](https://github.com/OpenJUIZ/juiz/issues/262)).
See the ["Windows" section of the hsjuiz README](https://github.com/OpenJUIZ/juiz/tree/main/bindings/hsjuiz#windows) for details.

</TabItem>
</Tabs>

Replace `/home/me`, `/Users/me` or `C:/Users/me` with your home directory (`~` cannot be used in `cabal.project`).
On Linux and macOS, the rpath is needed because GHC loads libjuiz_sdk together with hsjuiz when it runs Template Haskell.
The `build.sh` of the [juiz_examples_haskell](https://github.com/OpenJUIZ/juiz_examples_haskell) examples does everything from getting libjuiz_sdk and hsjuiz (from the juiz source) to building the examples, so you can also use it as a template.

See the [hsjuiz README](https://github.com/OpenJUIZ/juiz/tree/main/bindings/hsjuiz) for how to write them.

<Aside type="note">
For 0.2.5 and earlier, which are not on Hackage, get the juiz source at the tag of the same version (`git clone --depth 1 --branch v0.2.4 https://github.com/OpenJUIZ/juiz.git ~/juiz-0.2.4`) and add its `bindings/hsjuiz` to `packages:` in `cabal.project` (`packages: . /home/me/juiz-0.2.4/bindings/hsjuiz`). The [tutorial](/tutorial/first-process/haskell/) uses this way.
</Aside>

## Zig

Write components with [zigjuiz](https://github.com/OpenJUIZ/juiz/tree/main/bindings/zigjuiz) (`@import("juiz")`). You need Zig 0.17.x (Linux, macOS and Windows).
zigjuiz makes the C functions that juiz looks for from your Zig functions at comptime, so the result is a shared library linked to libjuiz_sdk, like C++ and Haskell.

### Supported Zig version

Zig is before 1.0, and its standard library and `build.zig` API change with each version. zigjuiz supports **only one Zig version** and stops the build on any other version.
The versions match as follows.

| juiz and zigjuiz | Zig |
| --- | --- |
| 0.3.3 and later (the first version that ships zigjuiz) | 0.17.x |

Install Zig from [ziglang.org](https://ziglang.org/download/). `pip install ziglang==0.17.1` also works; then run `python3 -m ziglang` instead of `zig` (the skeleton's `scripts/dev.sh` runs as `ZIG="python3 -m ziglang" scripts/dev.sh`).

### Getting zigjuiz and libjuiz_sdk

zigjuiz is in juiz's [GitHub Releases](https://github.com/OpenJUIZ/juiz/releases) as an archive per version, `zigjuiz-<version>.tar.gz`.
Add the same version as `juiz` to your project (the directory with `build.zig.zon`) with `zig fetch --save`.
Install libjuiz_sdk with `juiz sdk install` (it installs the same version as `juiz` into `~/.juiz/sdk/<version>`; `juiz sdk path` prints where).

```sh
juiz --version      # e.g. juiz <version>
juiz sdk install
zig fetch --save https://github.com/OpenJUIZ/juiz/releases/download/v<version>/zigjuiz-<version>.tar.gz
```

This writes `.zigjuiz = .{ .url = "...", .hash = "..." }` into `dependencies` of `build.zig.zon`. When you update juiz, run `zig fetch --save` again with the URL of the new version.
In a skeleton made with [`juiz pkg create <name> -b zig`](/guides/pkg/), `scripts/dev.sh` does this on its first run, so you do not have to.

In `build.zig`, call `zigjuiz.init` once and `addPlugin` for each plugin. zigjuiz finds libjuiz_sdk, links it and sets the rpath.

```zig title="build.zig"
const std = @import("std");
const zigjuiz = @import("zigjuiz");

pub fn build(b: *std.Build) void {
    const juiz = zigjuiz.init(b, .{
        .target = b.standardTargetOptions(.{}),
        .optimize = b.standardOptimizeOption(.{ .preferred_optimize_mode = .ReleaseSafe }),
    });
    const lib = juiz.addPlugin(.{
        .name = "increment_process_zig", // lib<name>.so; the same as the name in the conf
        .root_source_file = b.path("src/increment_process_zig.zig"),
    });
    b.installArtifact(lib);
}
```

`zig build --release` makes `libincrement_process_zig.so` (`.dylib` on macOS) in `zig-out/lib`.
If you call `juiz.installBundle(lib, .{})` instead of `b.installArtifact(lib)`, the plugin and libjuiz_sdk are put side by side in `zig-out/plugins/`, ready to go into a `.juizapp`.

<Tabs syncKey="platform">
<TabItem label="Linux">

The library is `lib<name>.so`. libjuiz_sdk is found at `juiz sdk path`, and the rpath has that directory and the plugin's own directory (`$ORIGIN`).

</TabItem>
<TabItem label="macOS">

The library is `lib<name>.dylib`. The target is `aarch64-macos` on Apple silicon and `x86_64-macos` on Intel. The rpath has the plugin's own directory (`@loader_path`) and the libjuiz_sdk directory.

</TabItem>
<TabItem label="Windows">

Run the same commands as on Linux and macOS in PowerShell. The library is `<name>.dll` without `lib`, and it goes to **`zig-out/bin`** (juiz does not use `<name>.lib` in `zig-out/lib`). Write the directory of the DLL in `path` of the configuration file.
Windows has no rpath, so zigjuiz copies `juiz_sdk.dll` to `zig-out/bin` during `zig build`.
It builds for Zig's default `x86_64-windows-gnu` and links `juiz_sdk.dll.lib` of libjuiz_sdk as is (no renamed copy like Haskell's is needed).

The skeleton of `juiz pkg create -b zig` works on Windows from the version after juiz 0.3.3 ([issue #588](https://github.com/OpenJUIZ/juiz/issues/588)). Use `scripts\dev.ps1` (`-Release` for a release build) and `scripts\pack.ps1` in PowerShell; the plugin goes to `app/plugins/x86_64-pc-windows-msvc/` as `<name>.dll` together with `juiz_sdk.dll`. The skeleton of 0.3.3 and earlier does not build on Windows, so write the `build.zig` above yourself there.

</TabItem>
</Tabs>

If libjuiz_sdk is somewhere else, pass `zig build -Djuiz-sdk=<extracted directory>`.
Zig can also build for other OSes and CPUs from one machine (`juiz sdk install --target <target>` and `-Dtarget`). For the details, the types you can use and how to return errors, see the [zigjuiz README](https://github.com/OpenJUIZ/juiz/tree/main/bindings/zigjuiz).

### Using the zigjuiz source

To try changes to zigjuiz, for example, you can use `bindings/zigjuiz` in the juiz source (`git clone https://github.com/OpenJUIZ/juiz.git`).
In your project, point to the zigjuiz of the source with `.path` in `build.zig.zon` instead of the Releases archive.
Zig does not take an absolute path in `.path`, so write it relative to the project directory.

```zig title="build.zig.zon (excerpt)"
.dependencies = .{
    .zigjuiz = .{ .path = "../juiz/bindings/zigjuiz" },
},
```

The zigjuiz in the source reads the C header of the same source (`bindings/cjuiz/include`) with a relative path, so adding it with `zig fetch --save=zigjuiz <source>/bindings/zigjuiz` does not build. Use `.path`.

When you create a skeleton, give the zigjuiz source with `--zigjuiz-dir`. `build.zig.zon` then points there with a relative path, and `scripts/dev.sh` does not get zigjuiz from Releases.

```sh
juiz pkg create my_juiz -b zig --zigjuiz-dir ~/juiz/bindings/zigjuiz
```
