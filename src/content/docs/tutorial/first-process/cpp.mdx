In this chapter you create a C++ (CMake) project skeleton with `juiz pkg create`, then build and run the Process in it, which adds two numbers and returns the sum.
You first read the Process code, which is the heart of the project, then run it and call it from a browser and from a terminal. Finally you read the other files in the skeleton.

<Aside type="tip" title="What you will learn">
- How to create a CMake project skeleton for writing Processes with `juiz pkg create`
- How to read the skeleton (`CMakeLists.txt`, `src/my_juiz.cpp`, `app/app.conf` and `scripts/`)
- A Process is an idempotent function that takes arguments and returns a result
- A Process has a "type name" and an "instance name"
- How to call a Process from outside and get the result back (call)
</Aside>

## Before you start

Prepare the following (Linux, macOS, or Windows).

- The `juiz` command, installed either with pip or with cargo as described in [Installation](/getting-started/install/)
- CMake 3.16 or later and a C++17 compiler (on Windows, Visual Studio 2022 or Build Tools for Visual Studio 2022 with "Desktop development with C++"; 2019 has also been confirmed to work)
- libjuiz_sdk and its headers, at the same version as `juiz`

C++ Processes are built against libjuiz_sdk, the shared library of functions that pass values to and from juiz.
Check the version of `juiz`, then extract libjuiz_sdk of the same version into `~/.juiz/sdk/<version>` (`%USERPROFILE%\.juiz\sdk\<version>` on Windows; to download it by hand, see [Language packages](/getting-started/packages/#c-and-haskell-libjuiz_sdk)).

## Create the skeleton

In a working directory, run the following command.

```sh
juiz pkg create my_juiz -b cpp -t process
```

| Part | Meaning |
| --- | --- |
| `my_juiz` | The project name. A directory with this name is created, and it also starts the type names. It must start with a lowercase letter and contain only lowercase letters, digits and `_` |
| `-b cpp` | The language (`rust` / `python` / `cpp` / `haskell`) |
| `-t process` | The kind of types to put in. `process` puts in just one Process. Without it a Container is added too, but this chapter starts with a Process only |

When it is created, the next commands to run are shown (you installed libjuiz_sdk in "Before you start", so you can skip the `curl ... install-juiz-sdk.sh` shown here).

```text
Created my_juiz (cpp, process) in ./my_juiz  [libjuiz_sdk 0.3.0]

Next steps:
  cd my_juiz
  # once: put libjuiz_sdk 0.3.0 in ~/.juiz/sdk/0.3.0
  curl -fsSL https://raw.githubusercontent.com/OpenJUIZ/juiz/main/scripts/install-juiz-sdk.sh | sh -s -- 0.3.0
  scripts/dev.sh                  # build and put the plugin and libjuiz_sdk in app/plugins/<target>/
  juiz -f app/app.conf -d         # start (keep it running)
  ...
```

Run all the following commands in `my_juiz`.

```sh
cd my_juiz
```

## The shape of the project

The skeleton contains the following files.

<FileTree>
- my_juiz/
  - CMakeLists.txt build settings
  - src/
    - my_juiz.cpp the Process code
  - app/
    - app.conf the start-up configuration file
    - juizapp.yaml information for the distribution package (.juizapp)
  - scripts/
    - dev.sh build and put the plugin in app/plugins/ (dev.ps1 on Windows)
    - pack.sh make the distribution package (pack.ps1 on Windows)
  - README.md how to use this skeleton
  - .gitignore
</FileTree>

In juiz, a Process is built as a shared library (`.so`, `.dylib` or `.dll`), and the `juiz` command loads it as a plugin.
In the skeleton, the types written in `src/my_juiz.cpp` are built together into one shared library, which is loaded and started as written in `app/app.conf`.
Start with the Process code, the heart of what you develop.

## The Process code: src/my_juiz.cpp

```cpp title="src/my_juiz.cpp"
#include <cstdint>
#include <optional>

#include "juiz/juiz.h"

// Process my_juiz_add. The arguments are passed in the order they are added to the manifest
static auto my_juiz_add_manif = ProcessManifest("my_juiz_add")
    .description("Returns a + b.")
    .add_int_arg("a", "the first value", 0)
    .add_int_arg("b", "the second value", 0);
std::optional<int64_t> my_juiz_add(int64_t a, int64_t b) {
    return a + b;
}
COMPONENT_PROCESS_FACTORY(my_juiz_add_manif, my_juiz_add);

// The manifest of the whole Component (the types in this plugin)
auto my_juiz_component_manifest() {
    return ComponentManifest("my_juiz")
        .description("my_juiz: a juiz component")
        .add_process(my_juiz_add_manifest());
}
DEFINE_COMPONENT_MANIFEST_ENTRY_POINT(my_juiz_component_manifest)
```

The comment at the top of the file is left out.

| Part | Meaning |
| --- | --- |
| `#include "juiz/juiz.h"` | The juiz C++ header, which comes with libjuiz_sdk |
| `my_juiz_add_manif` | The manifest (description) of the Process. The string in `ProcessManifest("my_juiz_add")` becomes the **type name** of the Process |
| `.description(...)` | The description of the Process, shown in the web UI and elsewhere |
| `.add_int_arg("a", "the first value", 0)` | Declares an integer argument `a`, with its description and default value (0). Arguments left out of a call take the default values |
| `my_juiz_add(int64_t a, int64_t b)` | The body of the Process. The arguments are passed in the order they are declared in the manifest |
| `std::optional<int64_t>` | The return value. Returning `std::nullopt` when there is no value makes it an error |
| `COMPONENT_PROCESS_FACTORY(...)` | Pairs the manifest with the body so that `juiz` can use it. This macro also generates the manifest function `my_juiz_add_manifest()` |
| `my_juiz_component_manifest()` | The list of types in this library. `ComponentManifest("my_juiz")` is the library name, and `.add_process(...)` lists the Processes |
| `DEFINE_COMPONENT_MANIFEST_ENTRY_POINT(...)` | Exposes the list of types so that `juiz` can load it |

Unlike Rust and Python, in C++ you write the type name and the arguments (name, description, default value) in the manifest yourself.

The skeleton is written in the form of a **Component**, which bundles several types into one library (hence the names `COMPONENT_...` and `ComponentManifest`).
In this chapter there is only one Process, but in chapter 2 you add a Container to the same file. Chapter 6 covers Components in detail.

## A Process is an idempotent function

`my_juiz_add` only takes arguments and returns a result.
It does not read or write any outside state, so the same arguments always give the same result (it is idempotent).
Thanks to this, Processes are easy to test, and they behave the same when you later connect them or move them to another machine.

`scripts/dev.sh` builds with cmake in the `build` directory, and copies the shared library (the plugin) and libjuiz_sdk to `app/plugins/<target>/`.
`<target>` is a name such as `x86_64-unknown-linux-gnu` that says which CPU and OS it is for; `juiz pkg target` prints it.
The plugin uses the libjuiz_sdk placed next to it, so the two always go together.

If you see `Could not find a configuration file for package "juiz_sdk"` or a version mismatch, check where you extracted libjuiz_sdk in "Before you start", and its version.

## Run it

Start `juiz`, passing the configuration file `app/app.conf` with `-f`.

```sh
juiz -f app/app.conf -d
```

| Option | Meaning |
| --- | --- |
| `-f <file>` | Read the configuration file, load the plugins and create the instances written in it |
| `-d` | Keep running (stop with Ctrl+C) |

On start-up it prints `juiz 管理画面: http://localhost:8000/ui/` (the address of the web UI). The HTTP broker is listening on port 8000.

## Call it from a browser

Leave `juiz` running and open the web UI at `http://localhost:8000/ui/` in a browser. You see a screen like this.

![The web UI. my_juiz_add0 under "処理 Process" on the left, and an ellipse for my_juiz_add0 in the diagram in the middle](../../../../assets/tutorial-web-ui/first-process-top.png)

The UI labels are in Japanese, with the English names used on this site shown in small type next to them. The screen has three parts.

- **The list on the left**: what is running. Under "処理 Process" (Process) you see the instance `my_juiz_add0` next to its type name `my_juiz_add`.
- **The diagram in the middle**: a diagram of the system. A Process is drawn as an ellipse; the large text is the instance name and the small text is the type name.
- **The panel on the right**: the properties (details) of what you select. It is empty because nothing is selected yet.

Click `my_juiz_add0` in the list or in the diagram, and its details appear in the right panel.
Scroll the right panel down to the heading "呼び出す" (Call), where you find input fields for the arguments `a` and `b`.
Enter `1` for `a` and `2` for `b`, then press the "呼び出す" (Call) button. If `3` appears under "結果" (Result), it worked.

![Close-up of the right panel: the argument table (a and b, type Int, default 0), the call form with a=1 and b=2, and the result 3](../../../../assets/tutorial-web-ui/first-process-call.png)

Look at the rest of the panel as well.

- The "引数" (Arguments) table lists each argument's name, type and default value (既定値). The default is what is used for an argument you leave out when calling, and it is the `default` you wrote in the code. ("拘束値", the bound value, is covered in chapter 3.)
- "既定値に戻す" (Reset to defaults) puts the default values (`0`) back in the fields. "JSON で編集" (Edit as JSON) lets you write all the arguments as JSON.
- "基本" (Basics) near the top shows the type name and the identifier (ID) of this Process.

Change the values and call it a few times. With the same arguments, you always get the same result.
See the [Web UI guide](/guides/web-ui/) for more on the web UI.

## Call it from a terminal

Whatever you did in the browser, you can also do from a terminal. Leave `juiz` running, open another terminal, go to `my_juiz` and call the Process.
First, list the running Processes.

```sh
juiz process list
# => ["http://127.0.0.1:8000/process/my_juiz_add0::my_juiz_add"]
```

The URL shown is the **ID** of this Process.
`http://127.0.0.1:8000` is where the Process lives (the broker), and the part after `process/` is "instance name`::`type name".
With [namespaces](/guides/namespace/), a namespace such as `robot1/` comes before the instance name. Without them, it looks as above.

Call the Process with this ID and arguments (call). Arguments are passed as JSON.

```sh
juiz process call "http://127.0.0.1:8000/process/my_juiz_add0::my_juiz_add" '{"a": 1, "b": 2}' -p
# => CapsulePtr((value:Value(3), option: []))
```

You passed `1` and `2` and got `3` back. `-p` prints the result.
Arguments you leave out take their default values (`0` for both `a` and `b`). Passing `'{"a": 5}'` returns `5`.

<Aside type="caution" title="Passing JSON in Windows PowerShell 5.1">
Windows PowerShell 5.1, which comes with Windows, drops the `"` in `'{"a": 1, "b": 2}'` before passing it to `juiz`.
Write a `\` before each `"`, as in `'{\"a\": 1, \"b\": 2}'`. In PowerShell 7.3 or later, the command above works as written.
</Aside>

Check that calling it again with the same arguments always gives the same result.

Both the `juiz` command and the web UI just call the same API over HTTP.
That means any program that speaks HTTP, in any language, can call a Process and get the result back.
This is **call**, the way of using juiz like a server and client.

## Read the other files in the skeleton

Besides the Process code, the skeleton contains files for building and starting it.

### The build settings: CMakeLists.txt

```cmake title="CMakeLists.txt"
cmake_minimum_required(VERSION 3.16)
project(my_juiz VERSION 0.1.0 LANGUAGES CXX)

set(CMAKE_CXX_STANDARD 17)
set(CMAKE_CXX_STANDARD_REQUIRED ON)
set(CMAKE_CXX_EXTENSIONS OFF)

if(NOT CMAKE_BUILD_TYPE AND NOT CMAKE_CONFIGURATION_TYPES)
  set(CMAKE_BUILD_TYPE Release)
endif()

set(JUIZ_VERSION "0.3.0")
if(WIN32)
  file(TO_CMAKE_PATH "$ENV{USERPROFILE}/.juiz/sdk/${JUIZ_VERSION}" JUIZ_SDK_DEFAULT_DIR)
else()
  set(JUIZ_SDK_DEFAULT_DIR "$ENV{HOME}/.juiz/sdk/${JUIZ_VERSION}")
endif()
set(JUIZ_SDK_DIR "${JUIZ_SDK_DEFAULT_DIR}" CACHE PATH "libjuiz_sdk directory")
find_package(juiz_sdk ${JUIZ_VERSION} EXACT CONFIG REQUIRED PATHS "${JUIZ_SDK_DIR}" NO_DEFAULT_PATH)

add_library(my_juiz SHARED src/my_juiz.cpp)
target_link_libraries(my_juiz PRIVATE juiz_sdk::juiz_sdk)
set_target_properties(my_juiz PROPERTIES
  LIBRARY_OUTPUT_DIRECTORY "$<1:${CMAKE_BINARY_DIR}/plugins>"
  RUNTIME_OUTPUT_DIRECTORY "$<1:${CMAKE_BINARY_DIR}/plugins>")
juiz_sdk_bundle(my_juiz)
```

The comments are left out. From the top:

| Part | Meaning |
| --- | --- |
| `cmake_minimum_required`, `project` | The CMake version to use, and the project's name and version. The only language is C++ (`CXX`) |
| `CMAKE_CXX_STANDARD 17` | The juiz C++ header uses C++17, so compile as C++17 |
| `JUIZ_VERSION`, `JUIZ_SDK_DIR` | Where libjuiz_sdk was extracted. The version of the `juiz` that created the skeleton is written here. If you put it somewhere else, change it with `cmake -D JUIZ_SDK_DIR=<dir>` (with `scripts/dev.sh`, the environment variable `JUIZ_SDK_DIR`) |
| `find_package(juiz_sdk ...)` | Looks for libjuiz_sdk in `JUIZ_SDK_DIR`. With `EXACT`, it stops here and tells you if the version differs. When found, it provides the target `juiz_sdk::juiz_sdk` |
| `add_library(my_juiz SHARED ...)` | Builds a shared library, the form `juiz` can load. The file name is `libmy_juiz.so` on Linux, `libmy_juiz.dylib` on macOS and `my_juiz.dll` on Windows |
| `target_link_libraries(... juiz_sdk::juiz_sdk)` | Links to libjuiz_sdk. This target also carries the settings for using the juiz headers |
| `LIBRARY_OUTPUT_DIRECTORY`, `RUNTIME_OUTPUT_DIRECTORY` | Put the built shared library in `build/plugins` |
| `juiz_sdk_bundle(my_juiz)` | Makes the plugin use the libjuiz_sdk placed next to it, and copies libjuiz_sdk to `build/plugins`. `scripts/dev.sh` copies the two to `app/plugins/<target>/` |

**Use the same libjuiz_sdk version as the one `juiz --version` shows.** `juiz` cannot load a plugin built with another version.
When you update `juiz`, install libjuiz_sdk of the same version and change the `JUIZ_VERSION` line too.

### The start-up configuration file: app/app.conf

This is the configuration file you passed to `juiz -f` (the comment at the top is left out).

```yaml title="app/app.conf"
"name": "my_juiz"
"option":
  "http_broker":
    "start": true
    "port": 8000
"plugins":
  "components":
    "my_juiz":
      "language": "c++"
      "path": "plugins/{target}"
"processes":
  - "type_name": "my_juiz_add"
    "name": "my_juiz_add0"
```

Configuration files are written in YAML. Roughly, this one says:

- `option`: start the HTTP broker on port 8000
- `plugins`: **load** the library of the Component `my_juiz` from `plugins/{target}` as a C++ plugin. `{target}` is replaced with the target name of the machine you run on, so the `app/plugins/<target>/libmy_juiz.so` put there by `scripts/dev.sh` is loaded (the path is relative to `app/`, the directory of the configuration file)
- `processes`: **create an instance** named `my_juiz_add0` from the loaded type `my_juiz_add`

Notice that "loading" and "creating an instance" are separate steps.
When juiz loads a library, it learns the Process **type** (how to make one). What you write in `processes` creates named **instances** from that type.
In the ID you called, `my_juiz_add0` is the instance name and `my_juiz_add` is the type name.
You can also create several instances with different names from the same type (covered in chapter 3).

### scripts and app/juizapp.yaml

`scripts/dev.sh` (`scripts\dev.ps1` on Windows) is the build script you used above.
`scripts/pack.sh` and `app/juizapp.yaml` are for bundling the finished building block into a single `.juizapp` file to hand out (it runs with just `juiz run`). The tutorial does not use them; see [Distributing apps (.juizapp)](/guides/app-package/).

## Try it yourself

- Change `src/my_juiz.cpp` to return the product (`a * b`) instead of the sum. Rebuild with `scripts/dev.sh` and restart `juiz`; `{"a": 3, "b": 4}` should now give `12`.
- Run `juiz pkg add process my_juiz_sub`. It adds a Process `my_juiz_sub` to `src/my_juiz.cpp` and `app/app.conf` (its body is `a + b`, the same as `my_juiz_add`). Change the added function to `a - b`, rebuild, and call it. `juiz process list` shows two Processes.

## Summary

- `juiz pkg create <name> -b cpp` creates a project skeleton that builds, starts and answers calls as is. The libjuiz_sdk version is written to match `juiz`.
- A C++ Process is built as a shared library linked to libjuiz_sdk, and `juiz` loads it as a plugin. In the skeleton, `scripts/dev.sh` builds it and puts it with libjuiz_sdk in `app/plugins/<target>/`.
- A Process is an idempotent function that only takes arguments and returns a result. In C++, you write the type name and the arguments in the manifest.
- juiz loads a library to learn a Process **type**, and creates named **instances** from it as written in the configuration file.
- A running Process has an ID shaped like a URL, and you can call it from outside with that ID and arguments (call).
