In this chapter you create a Rust project skeleton with `juiz pkg create`, then build and run the Process in it, which adds two numbers and returns the sum.
You first read the Process code, which is the heart of the project, then run it and call it from a browser and from a terminal. Finally you read the other files in the skeleton.

<Aside type="tip" title="What you will learn">
- How to create a Cargo project skeleton for writing Processes with `juiz pkg create`
- How to read the skeleton (`Cargo.toml`, `src/lib.rs`, `app/app.conf` and `scripts/`)
- A Process is an idempotent function that takes arguments and returns a result
- A Process has a "type name" and an "instance name"
- How to call a Process from outside and get the result back (call)
</Aside>

## Before you start

Install Rust and the `juiz` command by following "Install with cargo" in [Installation](/getting-started/install/) (Linux, macOS, or Windows).
On Windows, follow the steps in PowerShell. Where commands differ by OS, the tabs show each version.

```sh
juiz --version
# => juiz 0.3.4
```

`juiz pkg` is available from juiz 0.2.6. If your version is older, reinstall it with `cargo install juiz_app`.

## Create the skeleton

In a working directory, run the following command.

```sh
juiz pkg create my_juiz -b rust -t process
```

| Part | Meaning |
| --- | --- |
| `my_juiz` | The project name. A directory with this name is created, and it also starts the type names. It must start with a lowercase letter and contain only lowercase letters, digits and `_` |
| `-b rust` | The language (`rust` / `python` / `cpp` / `haskell`) |
| `-t process` | The kind of types to put in. `process` puts in just one Process. Without it a Container is added too, but this chapter starts with a Process only |

When it is created, the next commands to run are shown.

```text
Created my_juiz (rust, process) in ./my_juiz  [juiz_sdk =0.3.4]

Next steps:
  cd my_juiz
  scripts/dev.sh                  # build and put the plugin in app/plugins/<target>/
  juiz -f app/app.conf -d         # start (keep it running)
  ...
```

Run all the following commands in `my_juiz`.

```sh
cd my_juiz
```

## The shape of the project

The skeleton contains the following files.

<FileTree>
- my_juiz/
  - Cargo.toml crate settings
  - src/
    - lib.rs the Process code
  - app/
    - app.conf the start-up configuration file
    - juizapp.yaml information for the distribution package (.juizapp)
  - scripts/
    - dev.sh build and put the plugin in app/plugins/ (dev.ps1 on Windows)
    - pack.sh make the distribution package (pack.ps1 on Windows)
  - README.md how to use this skeleton
  - .gitignore
</FileTree>

In juiz, a Process is built as a shared library (`.so`, `.dylib` or `.dll`), and the `juiz` command loads it as a plugin.
In the skeleton, the types written in `src/lib.rs` are built together into one shared library, which is loaded and started as written in `app/app.conf`.
Start with the Process code, the heart of what you develop.

## The Process code: src/lib.rs

```rust title="src/lib.rs"
use juiz_sdk::prelude::*;

#[juiz_component_process(
    description = "Returns a + b."
    arguments = { default = { a = 0 b = 0 } }
)]
fn my_juiz_add(a: i64, b: i64) -> JuizResult<i64> {
    Ok(a + b)
}

juiz_component_manifest!(
    component_name = "my_juiz"
    processes = [ my_juiz_add ]
);
```

The comment at the top of the file and the test at the end (the `#[cfg(test)]` part) are left out.

| Part | Meaning |
| --- | --- |
| `use juiz_sdk::prelude::*;` | Brings in the macros and types used to write Processes (`juiz_component_process`, `JuizResult` and so on) |
| `#[juiz_component_process(...)]` | Makes this function a Process |
| `description` | The description of the Process, shown in the web UI and elsewhere |
| `arguments = { default = { a = 0 b = 0 } }` | The default values of the arguments, used for arguments left out of a call |
| `fn my_juiz_add(a: i64, b: i64)` | The function name `my_juiz_add` becomes the **type name** of the Process, and the parameter names `a` and `b` become the argument names |
| `-> JuizResult<i64>` | The return value. Return `Ok(value)` on success and `Err(...)` on failure |
| `juiz_component_manifest!(...)` | The list of types in this library. `component_name` is the library name, and `processes` lists the Process functions |

The Process itself is a short function that returns `a + b`. The macros generate the code that passes values to and from juiz.

The skeleton is written in the form of a **Component**, which bundles several types into one library (hence the names `juiz_component_*`).
In this chapter there is only one Process, but in chapter 2 you add a Container to the same file. Chapter 6 covers Components in detail.

`cargo test` runs the test at the end (it checks that `my_juiz_add` returns 3 for 1 and 2).

## A Process is an idempotent function

`my_juiz_add` only takes arguments and returns a result.
It does not read or write any outside state, so the same arguments always give the same result (it is idempotent).
Thanks to this, Processes are easy to test, and they behave the same when you later connect them or move them to another machine.

scripts\dev.ps1

`scripts/dev.sh` builds with `cargo build` and copies the shared library to `app/plugins/<target>/`.
`<target>` is a name such as `x86_64-unknown-linux-gnu` that says which CPU and OS it is for; `juiz pkg target` prints it.
The first build fetches and builds `juiz_sdk` and its dependencies, so it takes a while.

## Run it

Start `juiz`, passing the configuration file `app/app.conf` with `-f`.

```sh
juiz -f app/app.conf -d
```

| Option | Meaning |
| --- | --- |
| `-f <file>` | Read the configuration file, load the plugins and create the instances written in it |
| `-d` | Keep running (stop with Ctrl+C) |

On start-up it prints `juiz 管理画面: http://localhost:8000/ui/` (the address of the web UI). The HTTP broker is listening on port 8000.

## Call it from a browser

Leave `juiz` running and open the web UI at `http://localhost:8000/ui/` in a browser. You see a screen like this.

![The web UI. my_juiz_add0 under "処理 Process" on the left, and an ellipse for my_juiz_add0 in the diagram in the middle](../../../../assets/tutorial-web-ui/first-process-top.png)

The UI labels are in Japanese, with the English names used on this site shown in small type next to them. The screen has three parts.

- **The list on the left**: what is running. Under "処理 Process" (Process) you see the instance `my_juiz_add0` next to its type name `my_juiz_add`.
- **The diagram in the middle**: a diagram of the system. A Process is drawn as an ellipse; the large text is the instance name and the small text is the type name.
- **The panel on the right**: the properties (details) of what you select. It is empty because nothing is selected yet.

Click `my_juiz_add0` in the list or in the diagram, and its details appear in the right panel.
Scroll the right panel down to the heading "呼び出す" (Call), where you find input fields for the arguments `a` and `b`.
Enter `1` for `a` and `2` for `b`, then press the "呼び出す" (Call) button. If `3` appears under "結果" (Result), it worked.

![Close-up of the right panel: the argument table (a and b, type Int, default 0), the call form with a=1 and b=2, and the result 3](../../../../assets/tutorial-web-ui/first-process-call.png)

Look at the rest of the panel as well.

- The "引数" (Arguments) table lists each argument's name, type and default value (既定値). The default is what is used for an argument you leave out when calling, and it is the `default` you wrote in the code. ("拘束値", the bound value, is covered in chapter 3.)
- "既定値に戻す" (Reset to defaults) puts the default values (`0`) back in the fields. "JSON で編集" (Edit as JSON) lets you write all the arguments as JSON.
- "基本" (Basics) near the top shows the type name and the identifier (ID) of this Process.

Change the values and call it a few times. With the same arguments, you always get the same result.
See the [Web UI guide](/guides/web-ui/) for more on the web UI.

## Call it from a terminal

Whatever you did in the browser, you can also do from a terminal. Leave `juiz` running, open another terminal, go to `my_juiz` and call the Process.
First, list the running Processes.

```sh
juiz process list
# => ["http://127.0.0.1:8000/process/my_juiz_add0::my_juiz_add"]
```

The URL shown is the **ID** of this Process.
`http://127.0.0.1:8000` is where the Process lives (the broker), and the part after `process/` is "instance name`::`type name".
With [namespaces](/guides/namespace/), a namespace such as `robot1/` comes before the instance name (`process/robot1/my_juiz_add0::my_juiz_add`). Without them, it looks as above.

Call the Process with this ID and arguments (call). Arguments are passed as JSON.

```sh
juiz process call "http://127.0.0.1:8000/process/my_juiz_add0::my_juiz_add" '{"a": 1, "b": 2}' -p
# => CapsulePtr((value:Value(3), option: []))
```

You passed `1` and `2` and got `3` back. `-p` prints the result.
Arguments you leave out take their default values (`0` for both `a` and `b`). Passing `'{"a": 5}'` returns `5`.

<Aside type="caution" title="Passing JSON in Windows PowerShell 5.1">
Windows PowerShell 5.1, which comes with Windows, drops the `"` in `'{"a": 1, "b": 2}'` before passing it to `juiz`.
Write a `\` before each `"`, as in `'{\"a\": 1, \"b\": 2}'`. In PowerShell 7.3 or later, the command above works as written.
</Aside>

Check that calling it again with the same arguments always gives the same result.

Both the `juiz` command and the web UI just call the same API over HTTP.
That means any program that speaks HTTP, in any language, can call a Process and get the result back.
This is **call**, the way of using juiz like a server and client.

## Read the other files in the skeleton

Besides the Process code, the skeleton contains files for building and starting it.

### The crate settings: Cargo.toml

```toml title="Cargo.toml"
[package]
name = "my_juiz"
version = "0.1.0"
edition = "2021"
description = "my_juiz: a juiz component"
publish = false

[lib]
# cdylib: the plugin juiz loads (C ABI). rlib: for cargo test
crate-type = ["cdylib", "rlib"]

[dependencies]
# Same version as the juiz that made this skeleton (juiz --version)
juiz_sdk = "=0.3.4"
```

| Item | Meaning |
| --- | --- |
| `name` | The crate name. It becomes the file name of the shared library: `libmy_juiz.so` on Linux, `libmy_juiz.dylib` on macOS, and `my_juiz.dll` (no `lib` prefix) on Windows |
| `crate-type` in `[lib]` | `"cdylib"` is a shared library that other languages can load (a C-style dynamic library); this is the form `juiz` can load. `"rlib"` is there for `cargo test` |
| `juiz_sdk = "=0.3.4"` | The crate for writing Processes, and its version |

**Keep the `juiz_sdk` version the same as the one `juiz --version` shows.** The skeleton pins it with `=` to the version of the `juiz` that created it.
When you update `juiz`, change this line to the same version too.

### The start-up configuration file: app/app.conf

This is the configuration file you passed to `juiz -f` (the comment at the top is left out).

```yaml title="app/app.conf"
"name": "my_juiz"
"option":
  "http_broker":
    "start": true
    "port": 8000
"plugins":
  "components":
    "my_juiz":
      "language": "rust"
      "path": "plugins/{target}"
"processes":
  - "type_name": "my_juiz_add"
    "name": "my_juiz_add0"
```

Configuration files are written in YAML. Roughly, this one says:

- `option`: start the HTTP broker on port 8000
- `plugins`: **load** the library of the Component `my_juiz` from `plugins/{target}`. `{target}` is replaced with the target name of the machine you run on, so the `app/plugins/<target>/libmy_juiz.so` put there by `scripts/dev.sh` is loaded (the path is relative to `app/`, the directory of the configuration file)
- `processes`: **create an instance** named `my_juiz_add0` from the loaded type `my_juiz_add`

Notice that "loading" and "creating an instance" are separate steps.
When juiz loads a library, it learns the Process **type** (how to make one). What you write in `processes` creates named **instances** from that type.
In the ID you called, `my_juiz_add0` is the instance name and `my_juiz_add` is the type name.
You can also create several instances with different names from the same type (covered in chapter 3).

### scripts and app/juizapp.yaml

`scripts/dev.sh` (`scripts\dev.ps1` on Windows) is the build script you used above.
`scripts/pack.sh` and `app/juizapp.yaml` are for bundling the finished building block into a single `.juizapp` file to hand out (it runs with just `juiz run`). The tutorial does not use them; see [Distributing apps (.juizapp)](/guides/app-package/).

## Try it yourself

- Change `src/lib.rs` to return the product (`a * b`) instead of the sum. Rebuild with `scripts/dev.sh` and restart `juiz`; `{"a": 3, "b": 4}` should now give `12`.
- Run `juiz pkg add process my_juiz_sub`. It adds a Process `my_juiz_sub` to `src/lib.rs` and `app/app.conf` (its body is `a + b`, the same as `my_juiz_add`). Change the added function to `a - b`, rebuild, and call it. `juiz process list` shows two Processes.

## Summary

- `juiz pkg create <name> -b rust` creates a project skeleton that builds, starts and answers calls as is. The `juiz_sdk` version is written to match `juiz`.
- A Rust Process is built as a crate whose `crate-type` includes `"cdylib"`, and `juiz` loads it as a plugin. In the skeleton, `scripts/dev.sh` builds it and puts it in `app/plugins/<target>/`.
- A Process is an idempotent function that only takes arguments and returns a result. The name of the function with `#[juiz_component_process]` becomes the type name.
- juiz loads a library to learn a Process **type**, and creates named **instances** from it as written in the configuration file.
- A running Process has an ID shaped like a URL, and you can call it from outside with that ID and arguments (call).
