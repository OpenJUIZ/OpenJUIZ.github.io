In this chapter you create a Haskell (cabal) project skeleton with `juiz pkg create`, then build and run the Process in it, which adds two numbers and returns the sum.
You first read the Process code, which is the heart of the project, then run it and call it from a browser and from a terminal. Finally you read the other files in the skeleton.

<Aside type="tip" title="What you will learn">
- How to create a cabal project skeleton for writing Processes with `juiz pkg create`
- How to read the skeleton (`cabal.project`, the `.cabal` file, `src/MyJuiz.hs`, `app/app.conf` and `scripts/`)
- A Process is an idempotent function that takes arguments and returns a result
- A Process has a "type name" and an "instance name"
- How to call a Process from outside and get the result back (call)
</Aside>

<Aside type="note" title="On Windows">
The Haskell tutorial is written for Linux and macOS. `juiz pkg create` can make a Haskell skeleton on Windows, but it does not build there as is.
For how to write Haskell building blocks on Windows, see the "Windows" tab of [Haskell in Language packages](/getting-started/packages/#haskell).
</Aside>

## Before you start

Prepare the following (Linux or macOS).

- The `juiz` command, installed either with pip or with cargo as described in [Installation](/getting-started/install/)
- GHC 9.6 or later and cabal. You can install them with [GHCup](https://www.haskell.org/ghcup/)
- libjuiz_sdk at the same version as `juiz`
- The juiz source at the same version as `juiz` (for hsjuiz, the Haskell library)

Haskell Processes are written with hsjuiz, juiz's Haskell library, and built against libjuiz_sdk, the shared library of functions that pass values to and from juiz.
hsjuiz is also on Hackage from 0.2.6 (see [Packages for each language](/getting-started/packages/#haskell)), but this chapter gets the juiz source at the tag of your `juiz` version and uses its `bindings/hsjuiz`. It needs no `cabal update` and works the same for versions that are not on Hackage.

Check the version of `juiz`, then extract libjuiz_sdk of the same version into `~/.juiz/sdk/<version>` and get the juiz source into `~/juiz-<version>` (to download libjuiz_sdk by hand, see [Language packages](/getting-started/packages/#c-and-haskell-libjuiz_sdk)).

## Create the skeleton

In a working directory, run the following command.

```sh
juiz pkg create my_juiz -b haskell -t process
```

| Part | Meaning |
| --- | --- |
| `my_juiz` | The project name. A directory with this name is created, and it also starts the type names. It must start with a lowercase letter and contain only lowercase letters, digits and `_` |
| `-b haskell` | The language (`rust` / `python` / `cpp` / `haskell`) |
| `-t process` | The kind of types to put in. `process` puts in just one Process. Without it a Container is added too, but this chapter starts with a Process only |

When it is created, the next commands to run are shown (you prepared the hsjuiz source and libjuiz_sdk in "Before you start", so you can skip the `git clone` and `curl` shown here).

```text
Created my_juiz (haskell, process) in ./my_juiz  [hsjuiz 0.3.0]

Next steps:
  cd my_juiz
  # once: get hsjuiz 0.3.0 (the juiz source) in /home/me/juiz-0.3.0/bindings/hsjuiz
  git clone --depth 1 --branch v0.3.0 https://github.com/OpenJUIZ/juiz.git ~/juiz-0.3.0
  # once: put libjuiz_sdk 0.3.0 in /home/me/.juiz/sdk/0.3.0
  curl -fsSL https://raw.githubusercontent.com/OpenJUIZ/juiz/main/scripts/install-juiz-sdk.sh | sh -s -- 0.3.0
  scripts/dev.sh                  # build and put the plugin in app/plugins/<target>/
  juiz -f app/app.conf -d         # start (keep it running)
  ...
```

`/home/me` shows your own home directory (on macOS it looks like `/Users/me`).
If you create the skeleton before the preparation, it also warns that hsjuiz and libjuiz_sdk are not found, but the skeleton is fine as is. Prepare them afterwards.

Run all the following commands in `my_juiz`.

```sh
cd my_juiz
```

## The shape of the project

The skeleton contains the following files.

<FileTree>
- my_juiz/
  - cabal.project where hsjuiz and libjuiz_sdk are
  - my-juiz.cabal build settings
  - src/
    - MyJuiz.hs the Process code
  - app/
    - app.conf the start-up configuration file
    - juizapp.yaml information for the distribution package (.juizapp)
  - scripts/
    - dev.sh build and put the plugin in app/plugins/
    - pack.sh make the distribution package
    - bundle-plugin-deps.sh used by pack.sh
  - README.md how to use this skeleton
  - .gitignore
</FileTree>

In juiz, a Process is built as a shared library (`.so` or `.dylib`), and the `juiz` command loads it as a plugin.
In the skeleton, the types written in `src/MyJuiz.hs` are built together into one shared library, which is loaded and started as written in `app/app.conf`.
Start with the Process code, the heart of what you develop.

## The Process code: src/MyJuiz.hs

```haskell title="src/MyJuiz.hs"
{-# LANGUAGE OverloadedStrings #-}
{-# LANGUAGE TemplateHaskell #-}
module MyJuiz () where

import Juiz

-- | The manifest of the whole Component (the types in this plugin)
my_juiz_component :: ComponentManifest
my_juiz_component = componentManifest "my_juiz"
  & description "my_juiz: a juiz component"

-- | Process my_juiz_add
my_juiz_add_manifest :: ProcessManifest
my_juiz_add_manifest = processManifest "my_juiz_add"
  & description "Returns a + b."
  & addIntArg "a" "the first value" 0
  & addIntArg "b" "the second value" 0

my_juiz_add :: Int64 -> Int64 -> Int64
my_juiz_add a b = a + b

juizComponent 'my_juiz_component
  [ componentProcess 'my_juiz_add 'my_juiz_add_manifest
  ]
```

The descriptive comment at the top of the file is left out.

| Part | Meaning |
| --- | --- |
| The two `LANGUAGE` lines | Turn on `OverloadedStrings`, so string literals can be `Text`, and `TemplateHaskell`, used by `juizComponent` at the end |
| `import Juiz` | Imports hsjuiz |
| `my_juiz_component` | The name and description of this library (Component) |
| `my_juiz_add_manifest` | The manifest (description) of the Process. The string in `processManifest "my_juiz_add"` becomes the **type name** of the Process |
| `addIntArg "a" "the first value" 0` | Declares an integer argument `a`, with its description and default value (0). Arguments left out of a call take the default values |
| `my_juiz_add :: Int64 -> Int64 -> Int64` | The body of the Process. The arguments are passed in the order they are declared in the manifest. It is an ordinary pure function |
| `juizComponent 'my_juiz_component [...]` | Pairs the functions with their manifests and exposes them so that `juiz` can load them. `componentProcess` lists a Process |

As in C++, in Haskell you write the type name and the arguments (name, description, default value) in the manifest yourself.

The skeleton is written in the form of a **Component**, which bundles several types into one library.
In this chapter there is only one Process, but in chapter 2 you add a Container to the same file. Chapter 6 covers Components in detail.

## A Process is an idempotent function

`my_juiz_add` only takes arguments and returns a result.
It does not read or write any outside state, so the same arguments always give the same result (it is idempotent).
In Haskell, the type `Int64 -> Int64 -> Int64` says so (there is no `IO`).
Thanks to this, Processes are easy to test, and they behave the same when you later connect them or move them to another machine.

## Build

Build with `scripts/dev.sh`.

<Tabs syncKey="platform">
<TabItem label="Linux">

```sh
scripts/dev.sh
# => ...
#    app/plugins/x86_64-unknown-linux-gnu/libmy_juiz.so
```

</TabItem>
<TabItem label="macOS">

```sh
scripts/dev.sh
# => ...
#    app/plugins/aarch64-apple-darwin/libmy_juiz.dylib
```

On an Intel Mac, `aarch64-apple-darwin` is `x86_64-apple-darwin`.

</TabItem>
</Tabs>

`scripts/dev.sh` builds with `cabal build all` and copies the shared library to `app/plugins/<target>/`.
`<target>` is a name such as `x86_64-unknown-linux-gnu` that says which CPU and OS it is for; `juiz pkg target` prints it.
The first build also builds hsjuiz, so it takes a while.

If a path in `cabal.project` is wrong, `cabal build` stops because it cannot find hsjuiz or libjuiz_sdk. In that case, check the locations and versions you prepared in "Before you start".

<Aside type="caution">
The built plugin refers to the hsjuiz shared library inside `dist-newstyle`.
If you delete `dist-newstyle` or switch GHC, run `scripts/dev.sh` again.
</Aside>

<Aside type="note" title="If linking fails on macOS">
If the Command Line Tools installed are newer than the selected Xcode, GHC's link step can fail with `tapi error: ... unknown architecture`.
Build with the Command Line Tools' linker, like `DEVELOPER_DIR=/Library/Developer/CommandLineTools scripts/dev.sh` ([issue #143](https://github.com/OpenJUIZ/juiz/issues/143)).
</Aside>

## Run it

Start `juiz`, passing the configuration file `app/app.conf` with `-f`.

```sh
juiz -f app/app.conf -d
```

| Option | Meaning |
| --- | --- |
| `-f <file>` | Read the configuration file, load the plugins and create the instances written in it |
| `-d` | Keep running (stop with Ctrl+C) |

On start-up it prints `juiz 管理画面: http://localhost:8000/ui/` (the address of the web UI). The HTTP broker is listening on port 8000.

## Call it from a browser

Leave `juiz` running and open the web UI at `http://localhost:8000/ui/` in a browser. You see a screen like this.

![The web UI. my_juiz_add0 under "処理 Process" on the left, and an ellipse for my_juiz_add0 in the diagram in the middle](../../../../assets/tutorial-web-ui/first-process-top.png)

The UI labels are in Japanese, with the English names used on this site shown in small type next to them. The screen has three parts.

- **The list on the left**: what is running. Under "処理 Process" (Process) you see the instance `my_juiz_add0` next to its type name `my_juiz_add`.
- **The diagram in the middle**: a diagram of the system. A Process is drawn as an ellipse; the large text is the instance name and the small text is the type name.
- **The panel on the right**: the properties (details) of what you select. It is empty because nothing is selected yet.

Click `my_juiz_add0` in the list or in the diagram, and its details appear in the right panel.
Scroll the right panel down to the heading "呼び出す" (Call), where you find input fields for the arguments `a` and `b`.
Enter `1` for `a` and `2` for `b`, then press the "呼び出す" (Call) button. If `3` appears under "結果" (Result), it worked.

![Close-up of the right panel: the argument table (a and b, type Int, default 0), the call form with a=1 and b=2, and the result 3](../../../../assets/tutorial-web-ui/first-process-call.png)

Look at the rest of the panel as well.

- The "引数" (Arguments) table lists each argument's name, type and default value (既定値). The default is what is used for an argument you leave out when calling, and it is the `default` you wrote in the code. ("拘束値", the bound value, is covered in chapter 3.)
- "既定値に戻す" (Reset to defaults) puts the default values (`0`) back in the fields. "JSON で編集" (Edit as JSON) lets you write all the arguments as JSON.
- "基本" (Basics) near the top shows the type name and the identifier (ID) of this Process.

Change the values and call it a few times. With the same arguments, you always get the same result.
See the [Web UI guide](/guides/web-ui/) for more on the web UI.

## Call it from a terminal

Whatever you did in the browser, you can also do from a terminal. Leave `juiz` running, open another terminal, go to `my_juiz` and call the Process.
First, list the running Processes.

```sh
juiz process list
# => ["http://127.0.0.1:8000/process/my_juiz_add0::my_juiz_add"]
```

The URL shown is the **ID** of this Process.
`http://127.0.0.1:8000` is where the Process lives (the broker), and the part after `process/` is "instance name`::`type name".
With [namespaces](/guides/namespace/), a namespace such as `robot1/` comes before the instance name. Without them, it looks as above.

Call the Process with this ID and arguments (call). Arguments are passed as JSON.

```sh
juiz process call "http://127.0.0.1:8000/process/my_juiz_add0::my_juiz_add" '{"a": 1, "b": 2}' -p
# => CapsulePtr((value:Value(3), option: []))
```

You passed `1` and `2` and got `3` back. `-p` prints the result.
Arguments you leave out take their default values (`0` for both `a` and `b`). Passing `'{"a": 5}'` returns `5`.
Check that calling it again with the same arguments always gives the same result.

Both the `juiz` command and the web UI just call the same API over HTTP.
That means any program that speaks HTTP, in any language, can call a Process and get the result back.
This is **call**, the way of using juiz like a server and client.

## Read the other files in the skeleton

Besides the Process code, the skeleton contains files for building and starting it.

### The build settings: cabal.project and my-juiz.cabal

`cabal.project` says where hsjuiz, built together with the project, and libjuiz_sdk are.

```txt title="cabal.project"
packages: . /home/me/juiz-0.3.0/bindings/hsjuiz

active-repositories: :none

package hsjuiz
  extra-lib-dirs: /home/me/.juiz/sdk/0.3.0/lib
  ghc-options: -optl-Wl,-rpath,/home/me/.juiz/sdk/0.3.0/lib
```

The comments are left out. `/home/me` is your own home directory, written when the skeleton was created.

| Part | Meaning |
| --- | --- |
| `packages` | The packages built together: `.` is this project, and the other is hsjuiz in the juiz source you got in "Before you start" |
| `active-repositories: :none` | Do not fetch packages from Hackage. hsjuiz only uses packages that come with GHC, so it builds without `cabal update` |
| `extra-lib-dirs` of `package hsjuiz` | Where libjuiz_sdk, which hsjuiz links to, is |
| `ghc-options` of `package hsjuiz` | The rpath. GHC needs it to load libjuiz_sdk with hsjuiz when running Template Haskell, and the built plugin also finds libjuiz_sdk through it |

**Use the same hsjuiz and libjuiz_sdk version as the one `juiz --version` shows.** `juiz` cannot load a plugin built with another version.
The skeleton points to the locations for the version of the `juiz` that created it. When you update `juiz`, prepare the source and libjuiz_sdk of the same version, and change the version in these three places.

`my-juiz.cabal` has a `foreign-library` that builds the shared library.

```txt title="my-juiz.cabal"
cabal-version:      3.0
name:               my-juiz
version:            0.1.0
synopsis:           my_juiz: a juiz component
build-type:         Simple

foreign-library my_juiz
    type:             native-shared
    default-language: Haskell2010
    build-depends:    base >=4.18 && <5
                    , hsjuiz
    ghc-options:      -Wall -threaded
    if os(darwin)
        ghc-options:  -optl-Wl,-rpath,@loader_path
    else
        ghc-options:  -optl-Wl,-rpath,$ORIGIN
    hs-source-dirs:   src
    other-modules:    MyJuiz
```

| Part | Meaning |
| --- | --- |
| `foreign-library my_juiz` | Builds a shared library that other languages can load. From the name `my_juiz` you get `libmy_juiz.so` on Linux and `libmy_juiz.dylib` on macOS |
| `type: native-shared` | Makes it a shared library, the form `juiz` can load |
| `build-depends` | The packages used. `base >=4.18` means GHC 9.6 or later |
| `-threaded` | juiz calls Processes from other threads, so use the threaded runtime system |
| The `-rpath` lines | Let the plugin find the libraries placed next to it in a distribution package (.juizapp) |
| `other-modules: MyJuiz` | The module with the Processes |

### The start-up configuration file: app/app.conf

This is the configuration file you passed to `juiz -f` (the comment at the top is left out).

```yaml title="app/app.conf"
"name": "my_juiz"
"option":
  "http_broker":
    "start": true
    "port": 8000
"plugins":
  "components":
    "my_juiz":
      "language": "haskell"
      "path": "plugins/{target}"
"processes":
  - "type_name": "my_juiz_add"
    "name": "my_juiz_add0"
```

Configuration files are written in YAML. Roughly, this one says:

- `option`: start the HTTP broker on port 8000
- `plugins`: **load** the library of the Component `my_juiz` from `plugins/{target}` as a Haskell plugin. `{target}` is replaced with the target name of the machine you run on, so the `app/plugins/<target>/libmy_juiz.so` put there by `scripts/dev.sh` is loaded (the path is relative to `app/`, the directory of the configuration file)
- `processes`: **create an instance** named `my_juiz_add0` from the loaded type `my_juiz_add`

Notice that "loading" and "creating an instance" are separate steps.
When juiz loads a library, it learns the Process **type** (how to make one). What you write in `processes` creates named **instances** from that type.
In the ID you called, `my_juiz_add0` is the instance name and `my_juiz_add` is the type name.
You can also create several instances with different names from the same type (covered in chapter 3).

### scripts and app/juizapp.yaml

`scripts/dev.sh` is the build script you used above.
`scripts/pack.sh`, `scripts/bundle-plugin-deps.sh` and `app/juizapp.yaml` are for bundling the finished building block into a single `.juizapp` file to hand out (it runs with just `juiz run`). The tutorial does not use them; see [Distributing apps (.juizapp)](/guides/app-package/).

## Try it yourself

- Change `src/MyJuiz.hs` to return the product (`a * b`) instead of the sum. Rebuild with `scripts/dev.sh` and restart `juiz`; `{"a": 3, "b": 4}` should now give `12`.
- Run `juiz pkg add process my_juiz_sub`. It adds a Process `my_juiz_sub` to `src/MyJuiz.hs` and `app/app.conf` (its body is `a + b`, the same as `my_juiz_add`). Change the added function to `a - b`, rebuild, and call it. `juiz process list` shows two Processes.

## Summary

- `juiz pkg create <name> -b haskell` creates a project skeleton that builds, starts and answers calls as is. The locations of hsjuiz and libjuiz_sdk are written to match the `juiz` version.
- A Haskell Process is built as a shared library with cabal's `foreign-library`, and `juiz` loads it as a plugin. In the skeleton, `scripts/dev.sh` builds it and puts it in `app/plugins/<target>/`.
- A Process is an idempotent function that only takes arguments and returns a result. In Haskell, you write the type name and the arguments in the manifest and pair it with the function in `juizComponent`.
- juiz loads a library to learn a Process **type**, and creates named **instances** from it as written in the configuration file.
- A running Process has an ID shaped like a URL, and you can call it from outside with that ID and arguments (call).
