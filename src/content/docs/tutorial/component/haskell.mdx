So far you have built every Process, Container and ContainerProcess as a separate file (library), one per type.
In the configuration file in chapter 3, you also listed the types in `plugins` one by one so each file was loaded.

When you want to hand someone "the full set of parts for this camera", scattered files are inconvenient.
In this chapter you build a **Component** that bundles Processes, Containers and ContainerProcesses into one library, and load it from a configuration file.

<Aside type="tip" title="What you will learn">
- A Component is the **unit of distribution** that bundles several Processes, Containers and ContainerProcesses
- Types inside a Component keep their type names, and you create instances from them the same way as before
- `components` in `plugins` takes a single Component name instead of each type
</Aside>

## Prepare the samples

Keep using the example repository you cloned and built in chapter 4. The Component example was built along with everything else in chapter 4.
If you have not done that yet, follow [Prepare the samples in chapter 4 (Haskell)](/tutorial/connect/haskell/#prepare-the-samples).

The Component used in this chapter contains the following. Each works the same as what you built in the earlier chapters.

| Kind | What it does |
| --- | --- |
| Process | Adds 1 to its argument and returns it (same as `increment_process` in chapter 1) |
| Container | Holds one integer (same as the counter in chapter 2) |
| ContainerProcess | Reads or changes the Container's value |

## Read the Component code

[`component/ExampleComponent.hs`](https://github.com/OpenJUIZ/juiz_examples_haskell/blob/main/component/ExampleComponent.hs)

```haskell
{-# LANGUAGE OverloadedStrings #-}
{-# LANGUAGE TemplateHaskell #-}
-- | A Component that bundles a Process, a Container and ContainerProcesses in one library (example_component_hs).
--
-- Write each element's function and manifest, then expose them all together with juizComponent at the end.
module ExampleComponent () where

import Juiz

component :: ComponentManifest
component = componentManifest "example_component_hs"
  & description "Haskell component example."

-- Process: returns arg1 plus 1
incrementManifest :: ProcessManifest
incrementManifest = processManifest "example_component_hs_increment"
  & description "Adds 1 to arg1."
  & addIntArg "arg1" "value to be incremented" 1

increment :: Int64 -> Int64
increment arg1 = arg1 + 1

-- Container: holds one integer.
-- In a Component the Container and ContainerProcesses are in the same library, so the state type need not be in its own module
newtype ComponentContainer = ComponentContainer (IORef Int64)

containerManif :: ContainerManifest
containerManif = containerManifest "example_component_hs_container"
  & description "Holds an integer value."
  & addIntArg "value" "initial value" 0

createContainer :: Int64 -> IO ComponentContainer
createContainer value = ComponentContainer <$> newIORef value

-- ContainerProcess: returns the Container's value
getManifest :: ProcessManifest
getManifest = containerProcessManifest "example_component_hs_container_get" "example_component_hs_container"
  & description "Returns the value of the container."

containerGet :: ComponentContainer -> IO Int64
containerGet (ComponentContainer ref) = readIORef ref

-- ContainerProcess: adds arg1 to the Container's value
incrementContainerManifest :: ProcessManifest
incrementContainerManifest =
  containerProcessManifest "example_component_hs_container_increment" "example_component_hs_container"
    & description "Adds arg1 to the value of the container."
    & addIntArg "arg1" "value to be added" 1

containerIncrement :: ComponentContainer -> Int64 -> IO Int64
containerIncrement (ComponentContainer ref) arg1 = atomicModifyIORef' ref (\v -> (v + arg1, v + arg1))

juizComponent 'component
  [ componentProcess 'increment 'incrementManifest
  , componentContainer 'createContainer 'containerManif
  , componentContainerProcess 'containerGet 'getManifest
  , componentContainerProcess 'containerIncrement 'incrementContainerManifest
  ]
```

Each element's function and manifest have the same shape as when you wrote them on their own in chapters 1 and 2. Only the way they are exposed changes.

- Instead of `juizProcess`, `juizContainer` and `juizContainerProcess` for single elements, `juizComponent` at the end exposes everything together.
- `juizComponent` takes the Component's manifest (`componentManifest "example_component_hs"`; the string is the Component's name) and a list of the elements it contains. Each element pairs a function with a manifest using `componentProcess`, `componentContainer` or `componentContainerProcess`.
- One module holds several types, so each manifest gets its own name, such as `incrementManifest`.
- Which Container a ContainerProcess is bound to is given, as before, by the second argument of `containerProcessManifest` (the Container type name).
- The Container and the ContainerProcesses are in the same library, so the state type does not need its own module as in chapter 2.

The build is one `foreign-library` in [`juiz-examples-haskell.cabal`](https://github.com/OpenJUIZ/juiz_examples_haskell/blob/main/juiz-examples-haskell.cabal).

```txt
foreign-library example_component_hs
    import:           plugin
    type:             native-shared
    hs-source-dirs:   component
    other-modules:    ExampleComponent
```

This produces a single shared library: `build/plugins/libexample_component_hs.so` on Linux and `build/plugins/libexample_component_hs.dylib` on macOS.

What used to be split per type now lives in one library.
The bodies of the Processes and ContainerProcesses are unchanged. Processes are still idempotent functions, and only ContainerProcesses touch state.

## Read the configuration file

[`example_component.conf`](https://github.com/OpenJUIZ/juiz_examples_haskell/blob/main/example_component.conf)

```yaml
name: example_component
option:
  http_broker:
    start: true
    port: 8000
plugins:
  components:
    example_component_hs:
      language: "haskell"
      path: "./build/plugins"
processes:
  - type_name: example_component_hs_increment
    name: proc0
containers:
  - type_name: example_component_hs_container
    name: container0
    value: 100
    processes:
      - type_name: example_component_hs_container_increment
        name: increment0
      - type_name: example_component_hs_container_get
        name: get0
```

Compare it with the configuration file from chapter 3.

### plugins: one Component entry

```yaml
plugins:
  components:
    example_component_hs:
      language: "haskell"
      path: "./build/plugins"
```

In chapter 3 you listed types one by one in `process_factories` and `container_factories`, and each ContainerProcess under its Container.
With a Component, you write **just one Component name** in `components`. As in chapter 3, the key determines which file is loaded.

For the Component name `example_component_hs`, juiz loads `libexample_component_hs.so` (`libexample_component_hs.dylib` on macOS) from `./build/plugins`. The configuration file has no file extension in it, so the same file works on every OS.

That one entry loads every Process, Container and ContainerProcess type in the Component.

### processes and containers: created as usual

`processes` and `containers` are written exactly as in chapter 3. Put a type name from the Component in `type_name` and the instance name in `name`.
You can pass a Container's initial value the same way, too.

Where a type came from does not matter to the side creating instances.
A Component is for "distributing types together", and the instances you create behave exactly as if they had been loaded from separate files.

## Run it

Pass the configuration file with `-f`.

```sh
juiz -f example_component.conf -d
```

## Call it from outside

Leave `juiz` running, open another terminal, and look at the lists.

```sh
juiz process list
# => ["http://127.0.0.1:8000/process/proc0::example_component_hs_increment"]
juiz container list
# => ["http://127.0.0.1:8000/container/container0::example_component_hs_container"]
juiz container-process list
# => ["http://127.0.0.1:8000/container_process/get0::example_component_hs_container_get:container0", "http://127.0.0.1:8000/container_process/increment0::example_component_hs_container_increment:container0"]
```

Process, Container and ContainerProcess instances have all been created from types loaded from one file. The IDs look exactly like those in earlier chapters.
Call each of them.

```sh
juiz process call "http://127.0.0.1:8000/process/proc0::example_component_hs_increment" '{"arg1": 3}' -p
# => CapsulePtr((value:Value(4), option: []))
juiz container-process call "http://127.0.0.1:8000/container_process/get0::example_component_hs_container_get:container0" '{}' -p
# => CapsulePtr((value:Value(100), option: []))
juiz container-process call "http://127.0.0.1:8000/container_process/increment0::example_component_hs_container_increment:container0" '{"arg1": 5}' -p
# => CapsulePtr((value:Value(105), option: []))
juiz container-process call "http://127.0.0.1:8000/container_process/get0::example_component_hs_container_get:container0" '{}' -p
# => CapsulePtr((value:Value(105), option: []))
```

The Process adds 1 to its argument and returns it, and the ContainerProcesses change or read the Container's value.
From the caller's point of view, they are indistinguishable from what you built from separate files in chapters 1 to 3.

## A Component is the unit of distribution

As you have seen, bundling into a Component changes nothing about how Processes and Containers work or how you use them. Only **how the files are bundled** changes.

- **Authors** can write related Processes, Containers and ContainerProcesses in one project and distribute them as one library. For a camera, for example, a Container that opens and holds the camera, a ContainerProcess that reads images, and a Process that converts images can all be one Component.
- **Users** write one line in `components` under `plugins` to get every type inside. Which types to instantiate, and how many, is still decided freely with `processes` and `containers`.

In other words, Processes, Containers and ContainerProcesses are "units for running", while a Component is the "unit for distributing".

## Try it yourself

- Add another instance of `example_component_hs_increment` to `processes`. As in chapter 3, you can create any number of instances from types loaded from a Component.
- Add another Container (for example `container1`) and its ContainerProcesses to `containers`. `container0` and `container1` hold separate values.
- Add `connections` and `ecs` from chapter 4 and connect the first Process's output to `arg1` of the second Process you added. Types from a Component connect the same way as any other. `plugins` can list `components` and `process_factories` side by side, so you can also connect to a Process from a separate file, such as `increment_process` from chapter 3.
- You can also load a Component from the command line without a configuration file. With `-1`, juiz creates one instance of every type in the Component (named "type name + `0`" as in chapter 1).

<Tabs syncKey="platform">
<TabItem label="Linux">

```sh
juiz --component ./build/plugins/libexample_component_hs.so -l haskell -1 -d
```

</TabItem>
<TabItem label="macOS">

```sh
juiz --component ./build/plugins/libexample_component_hs.dylib -l haskell -1 -d
```

## Summary

- A Component bundles several Processes, Containers and ContainerProcesses into one library.
- In a configuration file, writing one Component name in `components` under `plugins` loads every type inside it.
- Creating instances, IDs, calling and connecting all work the same as when types are loaded from separate files. A Component does not change how things run; it is the **unit of distribution**.
