In the skeleton of chapters 1 to 3, you wrote the Process, Container and ContainerProcesses in one source, built them into one library, and loaded it with one line under `components` in `plugins` of `app/app.conf`.
The talker and listener examples in chapter 4, on the other hand, are separate files (libraries), one per type, loaded by listing the types one by one under `process_factories`.

When you want to hand someone "the full set of parts for this camera", scattered files are inconvenient.
In this chapter you take another look at the form the skeleton used, the **Component**, which bundles Processes, Containers and ContainerProcesses into one library, using the example repository, and compare it with one file per type.

<Aside type="tip" title="What you will learn">
- A Component is the **unit of distribution** that bundles several Processes, Containers and ContainerProcesses
- Types inside a Component keep their type names, and you create instances from them the same way as before
- `components` in `plugins` takes a single Component name instead of each type
</Aside>

## Prepare the samples

Keep using the example repository you cloned and built in chapter 4. The Component example was built along with everything else in chapter 4.
If you have not done that yet, follow [Prepare the samples in chapter 4 (Python)](/tutorial/connect/python/#prepare-the-samples).

The Component used in this chapter contains the following. Each works the same as what you built in the earlier chapters.

| Kind | What it does |
| --- | --- |
| Process | Adds 1 to its argument and returns it (an ordinary Process, like `my_juiz_add` in chapter 1) |
| Container | Holds one integer (same as the counter in chapter 2) |
| ContainerProcess | Reads or changes the Container's value |

## Read the Component code

[`component/example_component_python.py`](https://github.com/OpenJUIZ/juiz_examples_python/blob/main/component/example_component_python.py)

```python
from juiz import juiz_container, juiz_container_process, juiz_process


@juiz_process
def example_component_python_increment(arg1: int = 0) -> int:
    """Adds 1 to the argument and returns it"""
    return arg1 + 1


class IntegerContainer:
    def __init__(self, value: int):
        self.value = value


@juiz_container
def example_component_python_container(initial_value: int = 0) -> IntegerContainer:
    """A Container that holds one integer"""
    return IntegerContainer(initial_value)


@juiz_container_process(container_type="example_component_python_container")
def example_component_python_container_set(container, value: int = 0) -> int:
    """Sets the value of the Container"""
    container.value = value
    return container.value


@juiz_container_process(container_type="example_component_python_container")
def example_component_python_container_get(container) -> int:
    """Returns the value of the Container"""
    return container.value
```

The decorators are exactly the same as in `app/python/my_juiz.py` of the skeleton in chapters 1 and 2, and in the talker and listener of chapter 4. The only difference is that they are **placed in one file**.
When loaded as a Component, every decorated function in this file becomes a type of this Component. The file name `example_component_python` is the Component's name.

What the chapter 4 examples split per type now lives in one file.
The bodies of the Processes and ContainerProcesses are unchanged. Processes are still idempotent functions, and only ContainerProcesses touch state.

## Read the configuration file

[`example_component.conf`](https://github.com/OpenJUIZ/juiz_examples_python/blob/main/example_component.conf)

```yaml
name: example_component
option:
  http_broker:
    start: true
    port: 8000
plugins:
  components:
    example_component_python:
      language: python
      path: "./component"
processes:
  - type_name: example_component_python_increment
    name: increment0
containers:
  - type_name: example_component_python_container
    name: container0
    processes:
      - type_name: example_component_python_container_set
        name: set0
      - type_name: example_component_python_container_get
        name: get0
```

Compare it with `talker_listener.conf`, the configuration file from chapter 4.

### plugins: one Component entry

```yaml
plugins:
  components:
    example_component_python:
      language: python
      path: "./component"
```

In chapter 4 you listed types one by one in `process_factories` (Containers go in `container_factories`, with each ContainerProcess under its Container).
With a Component, as in `app/app.conf` from chapter 3, you write **just one Component name** in `components`. As with one file per type, the key determines which file is loaded.

For the Component name `example_component_python`, juiz loads `example_component_python.py` from `./component`.

That one entry loads every Process, Container and ContainerProcess type in the Component.

### processes and containers: created as usual

`processes` and `containers` are written exactly as in chapter 3. Put a type name from the Component in `type_name` and the instance name in `name`.
You can pass a Container's initial value the same way, too (this example omits it, so the value starts at `0`).

Where a type came from does not matter to the side creating instances.
A Component is for "distributing types together", and the instances you create behave exactly as if they had been loaded from separate files.

## Run it

Pass the configuration file with `-f`.

```sh
juiz -f example_component.conf -d
```

Run it in a terminal where the venv from chapter 4 is activated.

## Call it from outside

Leave `juiz` running, open another terminal, and look at the lists.

```sh
juiz process list
# => ["http://127.0.0.1:8000/process/increment0::example_component_python_increment"]
juiz container list
# => ["http://127.0.0.1:8000/container/container0::example_component_python_container"]
juiz container-process list
# => ["http://127.0.0.1:8000/container_process/set0::example_component_python_container_set:container0", "http://127.0.0.1:8000/container_process/get0::example_component_python_container_get:container0"]
```

Process, Container and ContainerProcess instances have all been created from types loaded from one file. The IDs look exactly like those in earlier chapters.
Call each of them.

```sh
juiz process call "http://127.0.0.1:8000/process/increment0::example_component_python_increment" '{"arg1": 3}' -p
# => CapsulePtr((value:Value(4), option: []))
juiz container-process call "http://127.0.0.1:8000/container_process/set0::example_component_python_container_set:container0" '{"value": 10}' -p
# => CapsulePtr((value:Value(10), option: []))
juiz container-process call "http://127.0.0.1:8000/container_process/get0::example_component_python_container_get:container0" '{}' -p
# => CapsulePtr((value:Value(10), option: []))
```

The Process adds 1 to its argument and returns it, and the ContainerProcesses change or read the Container's value.
From the caller's point of view, they are indistinguishable from types loaded from one file per type, as in chapter 4.

## A Component is the unit of distribution

As you have seen, bundling into a Component changes nothing about how Processes and Containers work or how you use them. Only **how the files are bundled** changes.

- **Authors** can write related Processes, Containers and ContainerProcesses in one project and distribute them as one library. For a camera, for example, a Container that opens and holds the camera, a ContainerProcess that reads images, and a Process that converts images can all be one Component.
- **Users** write one line in `components` under `plugins` to get every type inside. Which types to instantiate, and how many, is still decided freely with `processes` and `containers`.

<Aside type="tip" title="Distributing your skeleton">
The `my_juiz` you made in chapters 1 to 3 is also one Component. Run the skeleton's `scripts/pack.sh` (`scripts\pack.ps1` on Windows) to bundle the Component library and `app/app.conf` into a single `.juizapp` file; whoever receives it can run it with just `juiz run`. See "Distribute" in [Starting from a skeleton (juiz pkg)](/guides/pkg/#distribute) and [Distributing apps (.juizapp)](/guides/app-package/).
</Aside>

In other words, Processes, Containers and ContainerProcesses are "units for running", while a Component is the "unit for distributing".

## Try it yourself

- Add another instance of `example_component_python_increment` to `processes`. As in chapter 3, you can create any number of instances from types loaded from a Component.
- Add another Container (for example `container1`) and its ContainerProcesses to `containers`. `container0` and `container1` hold separate values.
- Add `connections` and `ecs` from chapter 4 and connect the first Process's output to `arg1` of the second Process you added. Types from a Component connect the same way as any other. `plugins` can list `components` and `process_factories` side by side, so you can also connect to a Process from a separate file, such as the talker from chapter 4.
- You can also load a Component from the command line without a configuration file. With `-1`, juiz creates one instance of every type in the Component (named "type name + `0`", as in the skeleton's `app/app.conf`).

```sh
juiz --component ./component/example_component_python.py -l python -1 -d
```

## Summary

- A Component bundles several Processes, Containers and ContainerProcesses into one file.
- In a configuration file, writing one Component name in `components` under `plugins` loads every type inside it.
- Creating instances, IDs, calling and connecting all work the same as when types are loaded from separate files. A Component does not change how things run; it is the **unit of distribution**.
